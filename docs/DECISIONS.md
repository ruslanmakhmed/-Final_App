# Решения

### 1. Python + Flask + PostgreSQL
Выбирали из Go, Python и Node, а для базы — из PostgreSQL и Redis. Приложение не оценивается, поэтому решила скорость написания, и выбран Python. PostgreSQL выбран, потому что у него штатные `pg_dump` для резервной копии и `pg_isready` для проб, а стойкость данных не требует отдельной настройки, как было бы с Redis (AOF/RDB). Приложение — один процесс gunicorn с потоками: счётчики метрик живут в памяти, и несколько воркеров в одном поде раздробили бы их.

### 2. Тонкий базовый образ без многоступенчатой сборки
Сравнивали `python:slim`, `python:alpine` и многоступенчатую сборку. Выбран `python:3.12.7-slim-bookworm`: в Alpine другая libc (musl), и готовые колёса `psycopg[binary]` на ней не ставятся, их пришлось бы собирать компилятором. Многоступенчатая сборка для интерпретируемого языка без компиляции ничего не даёт. Порядок слоёв такой: сначала `requirements.txt` и `pip install`, потом код.

### 3. Helm, а не Kustomize или голые манифесты
Требовалось два окружения с разным числом реплик и лимитами и подстановка тега образа при каждой выкатке. Helm решает это одним `--set image.tag=` и файлами values-dev/values-prod. Вдобавок `helm history` и `helm rollback` дают откат всего релиза целиком (ConfigMap + Deployment), а не только Deployment. Минус Helm — шаблоны нельзя проверить yamllint, поэтому для них в lint стоит `helm lint`. Мониторинг, наоборот, описан через Kustomize (`kubectl apply -k`): там нет параметров, но нужен `configMapGenerator`, чтобы `prometheus.yml`, правила и дашборд лежали отдельными файлами, которые можно линтовать.

### 4. База в кластере, StatefulSet + volumeClaimTemplates
Вариантов было два: Deployment с PVC или StatefulSet. Выбран StatefulSet: у пода стабильное имя `shortlink-db-0`, PVC привязан к нему, при удалении пода не удаляется, а при повторном создании подключается снова. Deployment при обновлении может на время поднять второй под с тем же RWO-томом. Сама база внутри кластера — компромисс учебного стенда: в production была бы управляемая база (см. CLOUD.md).

### 5. Две разные пробы
`/healthz` проверяет только живость процесса и никогда не смотрит в базу. `/readyz` проверяет базу. Если бы живость зависела от базы, её падение перезапускало бы все поды приложения по кругу, а это не помогает, только добавляет шума и нагрузки при восстановлении. С разными пробами под просто выходит из балансировки и возвращается сам.

### 6. Своя роль Ansible отвечает за фронтовой слой, Docker на узлах не ставится
Роль `edge` готовит узел принимать трафик: служебный пользователь, закрытый SSH, ufw с портами 22 и 80, nginx как обратный прокси по шаблону. Бэкенд задаётся переменными группы: dev смотрит на Compose (:8080), prod — на Ingress k3d (:8081). Расписание проверок сделано через **cron, а не systemd-таймер**: модуль `cron` идемпотентен сам по себе, это одна задача вместо двух юнитов (`.service` и `.timer`) и `daemon-reload`, а вывод всё равно попадает в журнал через `logger`. Systemd-таймер выиграл бы, если бы понадобились зависимости от других юнитов или `Persistent=true` для пропущенных запусков.

### 7. Конвейер — тонкая обёртка над `ci/run-stage.sh`
Каждая задача в `.github/workflows/ci.yml` вызывает `bash ci/run-stage.sh <стадия>`, поэтому команды локально и в конвейере совпадают по построению, а не по дисциплине. Выкатка запускается только по тегу `vX.Y.Z`: тег — это осознанное решение «эта версия идёт в кластер», и по нему же назван образ. Значит, откат — это «вернуться к предыдущему тегу», и видно, что именно работает в кластере.

### 7а. Свой GitLab CE и shell-раннер на узле Docker
Рассматривали три варианта: GitLab.com с общими раннерами, GitLab.com со своим раннером и свой GitLab CE. Общие раннеры GitLab.com не видят учебную сеть, так что deploy в k3s из них невозможен. Выбран свой GitLab CE на 192.168.1.26: весь цикл от push до кластера остаётся внутри стенда. Цена — ВМ с 3.6 ГБ RAM ниже минимума GitLab, поэтому добавлен swap 4 ГБ и урезана конфигурация (puma в single mode, sidekiq с concurrency 5, без встроенного Prometheus, KAS и registry). Раннер работает в режиме shell executor на 192.168.1.25, где уже есть Docker, свой реестр и kubeconfig. Задачи выполняют те же команды, что и человек у терминала, и образ между build и push не надо передавать архивом. Минус такого раннера: пользователь `gitlab-runner` состоит в группе `docker`, а это фактически root на узле. Для выделенного CI-узла это приемлемо, а в production здесь был бы docker executor на отдельной ВМ или Kaniko в кластере. GitLab и раннер описаны плейбуками `ansible/gitlab.yml` и `ansible/gitlab-runner.yml`.

### 8. Prometheus собирает каждый под, а не Service
Вариант со `static_configs: shortlink:8080` пришлось отвергнуть: Service каждый раз отправляет запрос в случайный под, и `rate()` по счётчикам разных подов даёт мусор. Через `kubernetes_sd_configs` (role: pod) у каждой реплики своя цель, и не готовый под тоже виден (`shortlink_db_up = 0`). Для этого нужны RBAC-права на чтение подов и узлов.
